SRP without classes

Functional programming changes the shape of the code, not the question of who owns change.

The misconception

“SRP is an object-oriented principle, so it does not apply to functions.” It applies whenever code can change for different reasons—whether that code is a class, function, module, or pipeline.

In functional TypeScript, SRP often looks like a separation between:

  • pure domain rules: data in, result out;
  • effects: database, email, logging, HTTP;
  • orchestration: the order in which the work happens.

Example 1: the mixed function

This function contains at least four change owners: product pricing, persistence, notifications, and observability.

async function placeOrder(order: Order): Promise<void> {
  const total = order.items.reduce(
    (sum, item) => sum + item.priceInCents * item.quantity,
    0,
  );

  await database.save({ ...order, total });
  await email.send(order.customerEmail, `Order total: ${total}`);
  logger.info('order.placed', { orderId: order.id, total });
}

It is not bad because it is long. It is risky because changes from several actors collide in one function. A new pricing rule should not require opening the email or database code.

Example 2: pure rule + explicit effects

Extract the business rule as a pure function. Then pass effects into the orchestration function:

const calculateTotal = (items: OrderItem[]): number =>
  items.reduce((sum, item) => sum + item.priceInCents * item.quantity, 0);

type Effects = {
  save: (order: PricedOrder) => Promise<void>;
  notify: (email: string, message: string) => Promise<void>;
  audit: (event: string, data: Record<string, unknown>) => void;
};

const placeOrder = (effects: Effects) => async (order: Order) => {
  const priced = { ...order, totalInCents: calculateTotal(order.items) };
  await effects.save(priced);
  await effects.notify(priced.customerEmail, 'Order confirmed');
  effects.audit('order.placed', { orderId: priced.id });
};
Order → pure pricing rule → orchestrator
↙ database effect   email effect   audit effect ↘

Composition makes dependencies visible without requiring a class hierarchy.

What improved? The pricing actor can change calculateTotal without touching integrations. The messaging actor can change notify without touching pricing. Tests can exercise the pure rule without a database, email provider, or logger.

Three smaller examples

Mixed

function formatAndSaveUser(user: User) {
  const body = JSON.stringify(user);
  fs.writeFileSync('user.json', body);
  return body;
}

Separated

const serializeUser = (user: User) =>
  JSON.stringify(user);

const saveText = (path: string, text: string) =>
  fs.writeFileSync(path, text);

Mixed

const parseAndValidateEmail = (raw: string) => {
  const email = raw.trim().toLowerCase();
  if (!email.includes('@')) throw new Error();
  return email;
};

Separated by rule

const normalizeEmail = (raw: string) =>
  raw.trim().toLowerCase();

const isValidEmail = (email: string) =>
  email.includes('@');
Do not over-split: normalizeEmail and isValidEmail might reasonably belong in one validation module if the same actor owns both. SRP is still about change ownership—not turning every expression into a function.

Your turn

Classify the parts of this function by responsibility, then propose a functional split:

async function registerUser(input: RegisterInput) {
  if (!input.email.includes('@')) throw new Error('Invalid email');
  const user = { ...input, createdAt: new Date() };
  await db.users.insert(user);
  await mailer.sendWelcome(user.email);
  logger.info('user.registered', { id: user.id });
  return user;
}
Reveal a strong answer

isValidEmail and buildUser are domain functions; saveUser, sendWelcome, and audit are effects. The orchestration function can receive those effects as function arguments. Whether validation and user construction share one module depends on who owns their changes.

Check yourself

  1. Does functional programming remove SRP?
  2. What is the strongest SRP signal in a function?
  3. Why pass effects into an orchestration function?
Answers
  1. No; it changes composition mechanisms, not reasons for change.
  2. Different actors would change different parts of its behavior.
  3. To make change ownership and testing boundaries explicit.
