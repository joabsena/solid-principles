Can I safely swap this implementation?

Four examples for recognizing behavioral substitution in everyday TypeScript.

The one question

If a caller works correctly with the promised type, will it still work correctly when given this implementation?

Think of a type as a behavioral contract. The contract includes what inputs are accepted, what results mean, which state changes happen, and what failures callers must handle. A subtype may implement that contract in its own way; it must not quietly change the contract.

Substitution in plain language: callers rely on the promise, not the implementation's name or internals. They should not need special-case code such as “if this is the read-only version, don't call write.”

Example 1 · A read-only store

Suppose FileStore promises both operations work for supported paths:

interface FileStore {
  read(path: string): Promise<string | undefined>;
  write(path: string, contents: string): Promise<void>;
}

class ReadOnlyFileStore implements FileStore {
  async read(path: string) { /* ... */ }
  async write(_path: string, _contents: string) {
    throw new Error('Read only');
  }
}

The method signatures fit. The behavior doesn't: a caller that accepts any FileStore may reasonably write to it. The subtype forces that caller to know which implementation it received.

Contract too broad

interface FileStore {
  read(path: string): Promise<...>;
  write(path: string, contents: string): Promise<void>;
}

Contracts match capability

interface ReadableStore {
  read(path: string): Promise<...>;
}
interface WritableStore extends ReadableStore {
  write(path: string, contents: string): Promise<void>;
}

A read-only store can implement ReadableStore. A backup job that writes should require WritableStore. Each caller states the capability it depends on.

Example 2 · “Every bird can fly”

This model makes flight part of the Bird contract:

interface Bird {
  fly(): void;
}

class Penguin implements Bird {
  fly(): void {
    throw new Error('Penguins cannot fly');
  }
}

The design mistake happened when the type promised more than all birds can do. Model the capability directly:

interface Bird { eat(): void; }
interface FlyingBird extends Bird { fly(): void; }

function migrate(bird: FlyingBird) { bird.fly(); }
function feed(bird: Bird) { bird.eat(); }

Penguins can be used wherever the general Bird promise is enough. Migration asks for the narrower FlyingBird capability.

Example 3 · Cache miss: value or exception?

Imagine a cache contract says a missing key returns undefined:

interface Cache {
  get(key: string): Promise<string | undefined>;
}

const loadGreeting = async (cache: Cache) => {
  const value = await cache.get('greeting');
  return value ?? 'Hello';
};

If one implementation throws CacheMissError instead, loadGreeting breaks even though get has the correct TypeScript signature. The implementation changed the meaning of “not found.”

Exceptions aren't automatically an LSP violation. If the contract says reads can fail with network errors, all implementations can report those failures. The violation is a subtype changing a case that the contract already defined, such as turning an ordinary miss into an exception.

Example 4 · A valid substitution

A memory store and a database store can both implement this contract:

interface KeyValueStore {
  get(key: string): Promise<string | undefined>;
  set(key: string, value: string): Promise<void>;
}

If both return undefined for a missing key and return a value after a successful write, a consumer can switch from memory to database without changing its logic. One may be slower internally. That is fine unless the contract promised a latency bound.

A useful way to inspect any contract

Contract partAskPossible LSP failure
Inputs / preconditionsWhat values must callers be allowed to pass?Subtype rejects an input the base accepts
Results / postconditionsWhat result or state change is promised?Subtype returns less, or changes the result's meaning
InvariantsWhat must stay true before and after operations?Subtype breaks a rule clients rely on
FailuresWhich failures are callers expected to handle?Subtype throws for a normal, supported case

The rectangle/square example from the previous lesson fits this table: independent width and height changes were part of the rectangle's behavior. A square preserved its own invariant by breaking that promise.

Practice: classify the change

Your turn

An interface Clock promises now() returns the current time. One implementation returns UTC; another returns local time as a timestamp. Can the caller safely swap them?

Reveal the reasoning

Usually yes if both return the same kind of instant (for example, epoch milliseconds). UTC versus local display is just an internal representation choice. But if one returns a local wall-clock value without timezone information, it changes the meaning and callers cannot safely substitute it. Write down what “current time” means in the contract.

Recall without peeking

  1. What does a subtype need to preserve?
  2. Does matching TypeScript signatures prove LSP?
  3. When is a different exception a violation?
  4. What is a clue that the base contract is too broad?
Answers
  1. The behavioral promises and invariants clients rely on.
  2. No. Signatures do not encode every semantic promise.
  3. When it replaces a normal outcome the contract promised, or exceeds the documented failure behavior.
  4. Some implementations reject, fake, ignore, or special-case one of its operations.
Primary source
Barbara Liskov and Jeannette Wing, A Behavioral Notion of Subtyping. Focus on the claim that properties established for a supertype should remain true for its subtypes.
