SOLID Principles · Lesson 1

Single Responsibility Principle

A class should have only one reason to change.

Code Review

"This class does too much. Can we split it up?" — You've heard this. But what does "too much" actually mean? And how do you decide where the split goes?

The Single Responsibility Principle (SRP) is the S in SOLID and the foundation everything else builds on. Get this wrong and the other four principles can't save you.

The definition — not what you think

Robert C. Martin's definition is precise:

A class should have only one reason to change.

Most people misinterpret this as "do one thing." That's wrong. SRP is not about functional cohesion — it's about who asks for changes.

A "reason to change" is a person or role (an actor) who could request a modification. If the CFO asks for a change to reporting and the CTO asks for a change to persistence, and both affect the same class, that class has two reasons to change — even if both changes are "one line."

The problem

Here's a UserService that does too many things for too many different people:

class UserService {
  constructor(private db: Database) {}

  // Concern: business rules (Product Owner)
  async register(data: RegisterDto): Promise<User> {
    const user = await this.db.user.create({ data });
    this.sendWelcomeEmail(user.email);
    this.logActivity('user.registered', user.id);
    return user;
  }

  // Concern: email delivery (DevOps / Marketing)
  async sendWelcomeEmail(to: string): Promise<void> {
    await mailer.send({ to, template: 'welcome' });
  }

  // Concern: observability (SRE / Platform team)
  private logActivity(event: string, userId: string): void {
    logger.info(event, { userId });
  }
}

Three different teams could ask for changes to this one class. That's three reasons to change — three axes of coupling. When the marketing team wants a new email template, they're touching the same file the product team modifies for business rules. Merge conflicts, regressions, fear.

The fix: separate by actor

Each concern moves to its own class, owned by the team that changes it:

// Team: Product — owns registration logic
class RegisterUserUseCase {
  constructor(
    private userRepo: IUserRepository,
    private notifier: INotificationService,
  ) {}

  async execute(data: RegisterDto): Promise<User> {
    const user = await this.userRepo.create(data);
    await this.notifier.userRegistered(user);
    return user;
  }
}

// Team: Platform — owns email delivery
class EmailNotificationService implements INotificationService {
  async userRegistered(user: User): Promise<void> {
    await mailer.send({ to: user.email, template: 'welcome' });
  }
}

// Team: SRE — owns logging / observability
class ObservabilityService {
  logUserCreated(userId: string): void {
    logger.info('user.registered', { userId });
  }
}

The mental model

BEFORE: one class
changed by 3 teams  ➜  User
Registration Email
Delivery Activity
Logging

Each box = one reason to change = one team

Common trap: Don't blindly split every function into its own class. SRP is about actors, not functions. If the same person owns both validateEmail and hashPassword, they can live together. The question is: who asks for changes?

Exercise: spot the responsibilities

Your Turn

Below is a simplified OrderProcessor. How many reasons to change (distinct actors) can you find? Write them down before expanding the answer.

class OrderProcessor {
  async process(order: Order): Promise<void> {
    if (!this.validateStock(order)) throw new Error('Out of stock');
    const total = this.calculateTotal(order);
    const receipt = await this.paymentGateway.charge(order.customerId, total);
    await this.inventory.decrement(order.items);
    await this.emailService.send(order.customerEmail, 'Order confirmed', receipt);
    this.auditLogger.log('order.placed', { orderId: order.id, total });
  }
}
Reveal answer

At least 4 reasons to change:

  1. Pricing rules (calculateTotal) — Finance / Product team changes discount logic
  2. Payment processing (paymentGateway.charge) — Payments team switches providers or adds fraud checks
  3. Inventory management (inventory.decrement) — Warehouse / Ops team changes allocation strategy
  4. Notifications (emailService.send) — Marketing team changes email templates or adds SMS

Also: stock validation and audit logging could be separate actors depending on org structure.

Check yourself (recall, don't peek)

  1. SRP says a class should have one reason to change. What is a "reason"?
  2. Is a 200-line class with 8 methods automatically an SRP violation?
  3. When shouldn't you split a class further?
Answers
  1. A person or role (actor) who could request a change — like "the CFO" or "the SRE team." Not a line of code.
  2. No. If all 8 methods serve the same actor, it's fine. SRP is about who asks for changes, not method count.
  3. When all the methods serve the same actor, or when splitting would create more coupling than it removes (e.g., tightly related logic that always changes together).
