SOLID Principles · Lesson 4

Liskov Substitution Principle

Every subtype must keep the promises its clients already rely on.

Code Review

“It implements the interface, so it must be safe to use here.” A type checker can confirm the method shapes match. It cannot confirm that the implementation keeps its behavioral promises.

The Liskov Substitution Principle (LSP) says that code written for a type should keep working when it receives a subtype. The key word is behavior: callers should not need to know which implementation they received in order to avoid surprises.

Practical version: a subtype may do the job differently, but it must still honor the contract that clients use.

A familiar violation: mutable rectangle and square

Suppose Rectangle promises that setting the width changes only the width, and setting the height changes only the height:

class Rectangle {
  constructor(protected width: number, protected height: number) {}

  setWidth(width: number): void { this.width = width; }
  setHeight(height: number): void { this.height = height; }
  area(): number { return this.width * this.height; }
}

class Square extends Rectangle {
  setWidth(width: number): void {
    this.width = width;
    this.height = width; // preserve square invariant; break rectangle promise
  }
}

This compiles in TypeScript. But a client of Rectangle may reasonably do this:

function resizeForBanner(shape: Rectangle) {
  shape.setWidth(5);
  shape.setHeight(4);
  return shape.area(); // client expects 5 × 4 = 20
}

A regular rectangle ends up 5 × 4, area 20. A square ends up 4 × 4, area 16. The caller accepted a Rectangle, but the subtype changed what the inherited operations mean.

Client expects → setWidth(5) → setHeight(4) → area = 20
Square changes both dimensions → area = 16

The hidden assumption in the base contract was independent width and height changes.

Important nuance: a square is mathematically a rectangle. The substitution problem comes from this particular mutable API: the rectangle contract permits independent changes. If the shared contract only promised an area, square and rectangle could both satisfy it.

Redesign around the promise clients need

Separate “has an area” from “can change width and height independently.” Then each shape implements only promises it can keep:

interface Shape {
  area(): number;
}

interface IndependentlyResizableRectangle extends Shape {
  setWidth(width: number): void;
  setHeight(height: number): void;
}

class Square implements Shape {
  // provides area(); no independent width/height setters
}
Rectangle ─implements→ Shape: area()
Square ──────────→ Shape: area()
Rectangle ─────────→ Independent resize capability

Now totalArea(shapes: Shape[]) can safely work with both. Code that needs independent resizing asks for the narrower resizing contract and receives only implementations that honor it.

How to spot an LSP problem

  1. State the base type’s behavioral promises in plain language.
  2. Find a client that uses only those promises.
  3. Substitute each subtype and see whether the client still behaves correctly.
  4. Look for subtype checks, unexpected exceptions, ignored methods, changed invariants, or surprising side effects.

In contract terms, a subtype should not require more from callers or guarantee less in return. It also needs to preserve invariants the supertype promises.

TypeScript reminder: structural typing checks that members exist with compatible types. It does not prove behavioral compatibility. The contract lives in documentation, tests, and the expectations clients are allowed to rely on.

Practice: the read-only file store

Your turn

An interface FileStore has read(path) and write(path, contents). A ReadOnlyFileStore implements write by throwing Error("Read only"). A backup job accepts any FileStore and calls both methods.

  1. What assumption does the backup job make about FileStore?
  2. Why does the read-only implementation break substitution?
  3. How would you split the contracts?
Reveal a strong answer

The backup job assumes every FileStore can write. The subtype violates that promise by throwing for a valid interface operation. Split into ReadableFileStore and WritableFileStore, or have the backup job depend only on the narrower capability it actually needs.

Check yourself (recall, don't peek)

  1. What does LSP protect?
  2. Why can code compile and still violate LSP?
  3. When should you split a base contract?
Answers
  1. The behavioral assumptions clients make about a supertype.
  2. The compiler checks member shapes, not every runtime promise.
  3. When some implementations cannot honor all of its promised behavior.
