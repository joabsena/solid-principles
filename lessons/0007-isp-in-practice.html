SOLID Principles · ISP Deepening

Who is this interface for?

More examples of shaping contracts around the clients that use them.

The key question

Which client needs which operations? Start from the callers, then shape their contracts.

ISP is easiest to see as a dependency problem. One object can have many capabilities, while each client sees only the capability it needs. The interfaces are views for clients; they do not always require separate implementation objects.

Example 1 · A timed door

A regular door has locking behavior. A timed door also needs to receive a timeout callback. If the timeout operation is added to the general Door interface, every ordinary door and every door client becomes coupled to timing.

interface Door {
  lock(): void;
  unlock(): void;
  isOpen(): boolean;
}

interface TimerClient {
  onTimeout(id: number): void;
}

class PlainDoor implements Door {
  private open = false;
  lock() { this.open = false; }
  unlock() { this.open = true; }
  isOpen() { return this.open; }
}

class TimedDoor implements Door, TimerClient {
  private open = false;
  lock() { this.open = false; }
  unlock() { this.open = true; }
  isOpen() { return this.open; }
  onTimeout(id: number) {
    if (this.open) console.log(`Door stayed open; timeout ${id}`);
  }
}

function showDoorStatus(door: Door) {
  return door.isOpen() ? 'open' : 'closed';
}

function registerAlarm(client: TimerClient) {
  // timer retains the client and calls onTimeout later
  return client;
}

TimedDoor implements both interfaces because it plays both roles. Door users depend on Door; the timer depends on TimerClient. A change to timeout handling does not make every door user depend on timer details.

Door users → Door view → TimedDoor object
Timer → TimerClient view ↗

One object; two narrow interfaces; separate clients.

This example comes from Robert C. Martin's original ISP article. It makes an important point: segregation is about what each client sees. You do not have to split one useful object into many tiny objects.

Example 2 · Read and write users separately

A profile page reads users. An edit screen saves them. Give those clients the contracts they use:

type User = { id: string; name: string };

interface UserReader {
  findById(id: string): Promise<User | undefined>;
}

interface UserWriter {
  save(user: User): Promise<void>;
}

function renderProfile(users: UserReader, id: string) {
  return users.findById(id);
}

function updateProfile(users: UserWriter, user: User) {
  return users.save(user);
}

A database repository can implement both interfaces. Each function still declares only the dependency it needs. This also makes tests smaller: the profile-page test needs a fake reader, not a fake repository with every write operation.

Example 3 · Publish versus subscribe

A message bus may support both sending and receiving events. But a command handler that emits an event need not depend on subscription methods, and a worker that listens need not depend on publishing:

type DomainEvent = { type: string; payload: unknown };

interface EventPublisher {
  publish(event: DomainEvent): Promise<void>;
}

interface EventSubscriber {
  subscribe(handler: (event: DomainEvent) => Promise<void>): void;
}

function completeOrder(events: EventPublisher, event: DomainEvent) {
  return events.publish(event);
}
function startWorker(events: EventSubscriber, handler: (event: DomainEvent) => Promise<void>) {
  events.subscribe(handler);
}

A full message-bus implementation can implement both. The important thing is that each client depends on its own direction of communication.

Example 4 · A good interface can have several methods

Suppose a transaction coordinator must either commit on success or rollback on failure. Both operations belong to the same client role and are used together:

interface Transaction {
  commit(): Promise<void>;
  rollback(): Promise<void>;
}

Splitting these into separate interfaces may make the transaction workflow harder to express without helping a real client. ISP asks whether a client depends on unrelated operations, not whether an interface has “too many” methods by some numeric rule.

Your turn

A payment API offers charge, refund, and settleBatch. Checkout calls only charge; customer support calls refund; a nightly finance job calls settleBatch.

  1. Which client-specific contracts might you define?
  2. Could one payment-provider object implement all of them?
  3. What design smell would tell you that you split too far?
Reveal a strong answer

Define contracts such as Charger, Refunder, and BatchSettlement, and pass each client only the capability it uses. One provider object can implement all three. If one client always needs all three together, or callers must juggle many tiny interfaces for one cohesive workflow, regroup them around that client role.

Recall without peeking

  1. Does ISP require a separate class for each interface?
  2. What should guide which operations are grouped together?
  3. What is one smell of a client depending on a fat interface?
Answers
  1. No. One object may implement several client-specific interfaces.
  2. The cohesive needs of the clients that use them.
  3. It must mock, implement, or depend on operations it never uses.
