SOLID Principles · Lesson 6

Interface Segregation Principle

Give each client the smallest useful contract for its job.

Code Review

“This class has to implement scan(), but it’s just a printer.” The interface may be describing a whole product instead of the capabilities each client uses.

The Interface Segregation Principle (ISP) says clients should not be forced to depend on operations they do not use. In TypeScript, think of “interface” broadly: it can be a declared interface, an abstract class, or simply the object shape a function accepts.

The problem: one contract for every office machine

A single interface may combine printing, scanning, and faxing:

interface OfficeMachine {
  print(document: Document): void;
  scan(): string;
  fax(number: string, document: Document): void;
}

class BasicPrinter implements OfficeMachine {
  print(document: Document): void { /* works */ }
  scan(): string {
    throw new Error('Not supported');
  }
  fax(_number: string, _document: Document): void {
    throw new Error('Not supported');
  }
}

The interface makes a basic printer pretend it can scan and fax. Meanwhile, a function that only prints invoices receives a dependency with unrelated capabilities:

function printInvoice(machine: OfficeMachine, invoice: Document) {
  machine.print(invoice);
}
Two principles meet here: the broad interface violates ISP because it burdens clients with unrelated operations. The “not supported” methods can also violate LSP because the implementation cannot keep the contract those methods imply.

The fix: contracts by capability

Split the broad interface into contracts that match useful client roles:

interface Printer { print(document: Document): void; }
interface Scanner { scan(): string; }
interface Fax {
  fax(number: string, document: Document): void;
}

function printInvoice(printer: Printer, invoice: Document) {
  printer.print(invoice);
}
printInvoice → Printer
BasicPrinter ─implements→ Printer
MultiFunctionDevice ─implements→ Printer + Scanner + Fax

A simple printer implements only Printer. A multifunction device can implement all three capabilities. The printing client works with either, and does not depend on scanning or faxing.

Why the client matters

“Small interface” is not a method-count contest. The useful question is: which operations belong together for this client? A printer driver may need a cohesive pair like print and cancelPrint; splitting those apart could make the client harder to use. Segregate when clients need different capabilities or implementations cannot support the same contract.

SignalWhat it suggests
“Not supported” methodSome implementation does not belong to this full contract
Different clients use different method groupsCreate role or capability interfaces
Every client uses every operationThe interface may already be cohesive
One-method interfaces everywhereYou may have split beyond useful client boundaries

Practice: media storage

Your turn

A service has this interface:

interface MediaStore {
  upload(file: Buffer): Promise<string>;
  download(id: string): Promise<Buffer>;
  delete(id: string): Promise<void>;
}

An avatar thumbnail component only downloads images. An archival job uploads and downloads, but must never delete. How might you reshape the contracts for those clients?

Reveal a strong answer

Define capabilities such as MediaReader with download, MediaWriter with upload, and MediaDeleter with delete. The thumbnail component accepts only MediaReader. The archival job can accept the reader and writer capabilities, without acquiring a deletion operation it must not use.

Whether upload and download should be one MediaReadWrite contract depends on whether those capabilities are normally needed together by the clients in this system.

Check yourself (recall, don't peek)

  1. Who should an interface be shaped around?
  2. What is a practical signal of a fat interface?
  3. Does ISP mean every method gets its own interface?
Answers
  1. The needs of the clients that depend on it.
  2. Implementations fake, ignore, or reject methods they do not support.
  3. No; group operations by cohesive client role or capability.
