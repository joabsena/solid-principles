SOLID Principles · Lesson 2

Open-Closed Principle

Make expected behavior addable without reopening stable policy.

Code Review

“Every new payment method means another if in checkout.” That is a signal: the business rule is stable, but its details are leaking into the coordinator.

The Open-Closed Principle (OCP) says a module should be open for extension and closed for modification. In practice: when a known kind of behavior grows, add a new implementation behind a stable contract instead of editing the stable orchestration repeatedly.

Important nuance: “Closed” does not mean “never edit this file again.” It means choosing closure against a particular, expected axis of change. You cannot predict every future change, so close the seams that your domain already tells you are volatile.

The smell: a growing conditional

Suppose a checkout service knows how every payment provider works:

class PaymentProcessor {
  async charge(provider: string, request: PaymentRequest): Promise<string> {
    if (provider === 'card') {
      // card SDK details
    }
    if (provider === 'pix') {
      // Pix API details
    }
    throw new Error('Unsupported provider');
  }
}

The first provider was cheap. The third, fourth, and fifth make the same class grow, and every change risks the checkout flow. This is not automatically bad: a tiny, stable set of cases can be clearer as a conditional. The signal is repeated change along the same axis.

The extension seam

Keep checkout responsible for the policy “charge this order.” Move provider-specific behavior behind a small contract:

interface PaymentMethod {
  charge(request: PaymentRequest): Promise<string>;
}

class Checkout {
  constructor(private readonly payment: PaymentMethod) {}

  pay(request: PaymentRequest): Promise<string> {
    return this.payment.charge(request);
  }
}

class PixPayment implements PaymentMethod {
  async charge(request: PaymentRequest): Promise<string> {
    // Pix-specific API details live here.
  }
}
Checkout policy  →  PaymentMethod
CardPayment PixPayment BoletoPayment

The stable policy depends on the contract; each volatile detail extends it.

How this connects to SRP

SRP asks, “Who asks this code to change?” OCP asks, “Can one expected kind of change be added without disturbing the code that should stay stable?” They reinforce each other:

ObservationQuestionDesign move
Provider details and checkout policy change for different reasonsSRPSeparate the actors
New providers keep editing checkoutOCPIntroduce PaymentMethod
Common trap: Do not create an interface for every class “just in case.” OCP is not a license for speculative abstraction. Add a seam when a change axis is real, repeated, or expensive to modify safely.

Your turn

A ReportExporter has a switch (format) for json, csv, and xml. Each branch knows a different serializer. Product expects more formats next quarter.

  1. What is the likely axis of change?
  2. Which part should become the stable policy?
  3. What would you name the extension contract?
Reveal a strong answer

The axis is export format. Keep “export this report” as the stable policy, and make each serializer implement a contract such as ReportExporter with export(report): string. Adding YAML should add YamlReportExporter, without editing the report orchestration.

Whether a factory or registry also needs changing is a separate design choice. OCP reduces change in the stable policy; it does not magically remove every composition change.

Check yourself (recall, don't peek)

  1. What does “closed for modification” protect?
  2. What signal tells you a conditional needs an extension seam?
  3. When is a conditional more pragmatic than an interface?
Answers
  1. Stable orchestration code remains unchanged when expected behavior grows.
  2. Repeated changes along one known axis keep editing the same stable code.
  3. When the cases are few, stable, and an abstraction would add needless complexity.
